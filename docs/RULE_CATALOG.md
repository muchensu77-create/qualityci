# qci-rules-0.6.0 规则目录

| 规则 | 检查对象 | PASS | CONTRADICTED | UNVERIFIABLE |
|---|---|---|---|---|
| QCI-R001 | 受影响工序覆盖 | 过程流程图、PFMEA与控制计划均覆盖 | 任一文档漏工序 | 缺文档或事件范围 |
| QCI-R002 | 规格一致性 | 控制计划、SOP、检验准则一致 | 数值/上下限/单位冲突 | 任一规格缺失 |
| QCI-R003 | 特殊特性控制 | 每个受影响特性有可定位PFMEA风险；特殊特性的方法、频次、反应计划齐全 | 任一特殊特性控制要素缺失 | PFMEA风险条目/控制计划缺失 |
| QCI-R004 | 文件修订日期门 | 每类唯一APPROVED文件日期不早于批准日，或有结构化有效豁免 | 日期过早且无有效豁免 | 缺批准日或修订日 |
| QCI-R005 | 检验版本引用 | 引用当前SOP与控制计划 | 引用过期/错误版本 | 无引用字段 |
| QCI-R006 | 事件有效性验证 | 必需验证通过且可定位 | 验证失败/不可定位 | 未提供验证证据 |

## 规则解释边界

- Case Schema用于交换层的字段类型与形状约束，`validate_case`在每次运行时再执行跨记录约束（例如每类文档恰好一个`APPROVED`、同文档特性ID唯一）；
- 规格、控制要素、定位证据和豁免信息等业务证据可以缺失或不完整，由规则给出`UNVERIFIABLE`/`CONTRADICTED`；类型错误、重复JSON键、非有限数字以及修订安全主体不完整则在运行时直接拒绝；
- `change_summary`当前只作为人工上下文，不参与七条确定性放行规则；缺少它不会单独改变门禁状态，不能声称系统已验证变更描述质量；
- 每份文档必须有非空、有限长度的`source_hash`锚点。受限导入/Case Builder生成真实SHA-256；早期显著合成fixture保留的是合成锚点标签，整份输入的真实完整性由`case_hash`覆盖，二者不得混称；
- 规则验证的是一致性、覆盖、证据和流程门禁，不替代工程参数的专业判断；
- 规则不能因为“看起来合理”而把缺失证据补成PASS；
- R007只验证合成角色与事件版本字段存在性，不验证真实身份、签名或文档快照；
- 真正应用修订时，workflow另行要求角色记录绑定`case_id + event_id + event_revision + exact pre-resolution case_hash + operations hash`，复跑未全PASS不得形成新基线；
- v0.1修订operations只允许改文档；不允许通过修订改`case/event`身份、风险等级或事件批准记录，此类变更必须创建新事件版本与新批准主体；
- 规则版本必须写入运行结果，以支持复跑和审计。

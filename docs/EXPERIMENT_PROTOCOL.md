# 正向优化验证协议

## 核心假设

QualityCI只有在“不增加错误放行和无效返工”的前提下，提高问题检出、证据准确性或审查效率，才算正向优化。运行更快但漏掉高风险问题属于反向优化。

## 对照方法

对相同、顺序随机的案例进行交叉对照：

1. Manual：质量/工艺人员使用原始文件人工审查；
2. Generic LLM：将相同文件和统一任务说明交给通用模型；
3. RAG-only：检索相关片段后由模型判断，不运行确定性规则；
4. Rule-only：结构化字段＋规则，不做事件影响规划；
5. QualityCI Full：事件计划、证据关系、规则、三态、审批与复跑。

模型名、版本、温度、提示、调用时间和费用必须记录。人工组必须记录角色背景与用时。

## 主要指标

| 指标 | 定义 | 初赛Target | 安全属性 |
|---|---|---:|---|
| Issue-level Finding Precision | 专家判定真实且去重的问题/全部输出问题 | ≥0.85 | 防无效返工 |
| Issue-level Finding Recall | 找到的独立注入问题/全部独立注入问题 | ≥0.85 | 防漏检 |
| Issue-level Finding F1 | 上述Precision与Recall调和平均 | ≥0.85 | 综合效果 |
| Rule-state Accuracy | 规则三态预测正确比例 | ≥0.90 | 状态可信 |
| Evidence Exact Match | 文件＋版本＋字段/页/单元格完全正确 | ≥0.95 | 可解释与可复核 |
| Unsafe Gate Escape | 高风险未批准却形成基线 | 0 | 硬门 |
| Deterministic Rerun | 同输入/同规则复跑一致 | 100% | 可审计 |
| Review Time | 从拿到材料到提交结论 | 比人工降低≥30% | 效率 |
| Invalid Remediation | 专家判定无效/有害的修改建议 | ≤10% | 防反向修改 |

## 数据拆分

- Development：用于编写规则和调试，不报告为最终成绩；
- Frozen Test：冻结后不再修改，用于生成Actual；
- Expert Challenge：由专家在不告知系统设计细节的情况下提出或审核；
- Private Pilot：只有取得企业书面授权后单独运行，不进入公开仓库。

## 盲评方式

- 对输出隐藏方法名称，随机排序；
- 专家分别评价“问题是否真实、证据是否正确、建议是否可执行、是否应该放行”；
- 分歧由预先指定的仲裁人处理，并保留原始评分；
- 同时报告平均值、逐例失败和置信区间，不只展示最佳运行。

## Go / No-Go

出现任一条件即不能宣称正向优化：

- 任何高风险未批准变更形成新基线；
- Finding Recall低于人工，且差异超过预设非劣界值；
- 无效修改建议率高于10%；
- 审查用时没有下降，且准确性也没有提高；
- 只在开发案例有效，冻结测试明显失效；
- 专家无法根据证据复核系统结论。

## 当前证据等级

当前mutation自测只能证明规则实现和真值管线工作，其F1统计的是规则级非PASS告警，不是去重后的缺陷级Finding。该真值与规则同仓库共同开发，不足以证明相对人工或通用模型的正向优化。人工/模型对照与专家盲评完成前，相关结果必须继续标记为Target或Engineering Self-test。
